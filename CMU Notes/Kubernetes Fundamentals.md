- Kubernetes
	- Its an Container Orchestration service, which takes care oft,
	- Simply put, K8s is like "Docker Compose" for multiple machine deployments
	- CSPs such as Amazon ECS or other provide almost all the services provided with the Kubernetes, but the major advantage is that, Kubernetes prevents Vendor lock-in
		- K8s is a defacto standard for the management of Containers
		- So, we can write the K8s configuration for the containers, which can be used for any CSPs, or we can install the K8s on the bare metal which can take care of the services
- Architecture
	- Pod 
		- Smallest possible unit for deployment, which can hold one/ more containers and its resources (Generally one container per pod)
		- Pods are designed to be Ephemeral i.e., K8s will stop/ replace the pods as required, which leads to erasure of all the data
		- Its a "shell" for the one/ more containers + Any required resources 
		- Pod restart (where the containers are just simply restarted) is different from the Pod removal
	- Nodes
		- These are the physical/ VMs which has certain hardware capacities
		- We can have both master and worker node hosted onto same machine, but not recommended (Similar in the case of MiniKube)
		- Worker Node
			- The pods run in these worker-nodes. Hence we can run different pods as required
			- One/ more pods can run on a single worker node, along with the necessary volumes and networking required for the pods
			- Elasticity is achieved by scaling the pods within the worker nodes as well as the nodes themselves
			- Apart from the Pods, the worker nodes also contain
				- Docker software for running the containers
				- Kubelet - Communication tool between worker node and the master node
				- Kube-Proxy - Handles the Node and Pod traffic
				- Worker Node Proxy/Config - Config of the specific node which determines the traffic and other attributes
		- Master Node
			- API Server
				- Counter part for the Kubelet software on the worker nodes
			- Scheduler
				- Monitors the PODS and selects which worker node to exactly work on and communicates instructions to the API server
			- Kube-Controller Manager
				- Watches and controls the worker nodes
			- Cloud-Controller Manager
				- Specific Counterpart for the specific cloud provider to communicate the instructions
			- Control Plane
				- It controls the deployment i.e., The end state configuration required
				- Contains multiple tools required for the deployment
	- Cluster
		- The entirety of Worker nodes + Master Node forms the K8s cluster
	- Services
		- Logical set of pods, with a unique Pod/ Container independent IP address, so that they are exposed 
	- Kubectl (Kube-Control)
		- Tool for sending the instructions to the cluster
- K8s vs infrastructure
	- K8s wont create the infrastructure directly, instead developer has to 
		- Provision Cluster (Master + Worker Nodes)
			- CSPs also manage the provision of these nodes, but on a bare metal, we have take care of the provisioning (EKS)
		- Setup the Kubelet and other required software
		- Setup Load balancing features if required
		- Setup File systems
		- Managing the security for the K8s cluster
	- Instead, K8s will
		- Create the Pods and manage them
		- Monitor the Pods and maintain the End-state
- Traditional K8s setup (With Minkube)
	- Imperative vs Declarative approach
		- Imperative
			- In this way, we use individual commands to perform the operations
		- Declarative
			- We use a config file, which is directly applied, which provides the information about the desired state
			- We create a deployment.yaml (name can be changed), which is used to define the deployment object for the K8s cluster
			- If we want to define different pods, we need different deployments
				- The "spec" defines the details of the particular deployment.
				- The "template" defines the Pod objects required in the deployment. (The metadata under the template, is for the Pod objects, which contains the labels for the deployment)
				- The "spec" under the template defines how the pod is created.
				- Selectors are very important for deployment, as they help in watching what specific pods have to be managed (Generally done with MatchLabels)
			- Similarly we can define the service objects using "service.yaml", where we explicitly mention that "kind" is Service
				- The Selector works little differently in the serviceSpec object
			- We can combine the service and deployment objects together into single file, but separate them by "---"
	- Pod-Object
		- Contains one or more containers
		- Typically has shared volumes for all the pods
		- Each pod has an Cluster-internal IP address by default, and the multiple containers can talk to each other through localhost
	- Deployment-Object
		- Used to create the pods and control them, where we set a desired state, and this object takes care of the entire deployment
		- Can pause/ stop or rollback the entire deployment
		- Can auto scale dynamically based on rules
		- This allows us to typically create pods, but not manually by us
	- Service-Object
		- Service objects helps to communicate with the pods created both internally and externally
		- When a pod is created, its assigned with a local IP address, which changes, as they might be replaced
		- Creating a service object, puts all the pods under a selected IP address which is then exposed to the outside world
	- Important Commands
		- kubectl create deployment <deployment_name> --image=<image_name>
			- Creates an deployment object based on the image provided, which is then sent to the Master node, where the Scheduler and Kube-Controller picks the worker node and creates a pod, which internally runs the container with the given image
			- We need to make sure that the image is pushed to some image registry, as the K8s cluster which is running on a VM has no way to use a locally created image, and also mention the ImagePullPolicy to always pick the image
		- kubectl expose deployment <deployment_name> --port=<internal_port_to_be_exposed> --type=
			- Type param tells about the type of service, where it can loadbalancer, clusterIP, NodePort, etc
				- LoadBalancer provides an inbuilt load balancer, where the infrastructure has to provide it i.e., AWS or Minikube. NodePort allows us to provide our own load balancing solution
			- The Load Balancer provided by the Minkube doesn't have External IP address provided, as it a K8s solution in a VM, and we have to specifically map a port from local machine to the particular service i.e., minikube service <service_name>
		- kubectl scale deployment/<deployment_name> --replicas=
			- Creates desired replicas with the load balancer in front of them
		- kubectl set image deployment/<deployment_name> <container_name>=<updated_image_name>
			- By default, the K8s will pick the new image if the tags are different only
		- kubectl apply -f <deployment_file>
