- Spark
	- Drawbacks of Mapreduce leading to Spark
		- One of the biggest drawbacks for the mapreduce is for the iterative computation of large datasets, where we use the disk storage to hold intermediate results, even though we had great flexibility, but it had huge overhead
			- Understand Relative cost of using In memory vs Disk and Network
		- Iterative operations on a graph is also not recommended
			- There was an explosion of Models over here with different features, why cant we have them all
	- How Spark solves them all
		- How in-memory computation works
			- Keep and the share the datasets in the main memory
			- Why this was not thought in first place for mapreduce = because of volatility and inability to store the pre and post mutations of the data
		- Inability to store the pre and post mutations of the data
			- First of all we dont need to store intermediate data if we know we can derive them back from the source
	- We solve it using RDD (resilient distributed datasets)
		- RDD only has few operations - map, groupBy, filter, sample, flatMap
		- So, if there is any issue with the data, we can traceback to the previous checkpoint that can be a cache or source, and reapply those computations exactly on that particular shard of data
		- RDD are immutable, and deterministic
		- RDD are compatible with HDFS as well, as they support streaming Appends
	- How RDD solves Fault tolerance
		- RDD has 2 properties
			- Immutability - once constructed, cant be changed
			- Allow only Functional transformations - map, filter, reduce which are deterministic and can run in parallel
	- Spark Job Architecture and components
		- Driver program - main program/ application
		- Context - Sparkcontext - handle to the spark cluster
		- Worker program - Program that runs on the cluster nodes
		- Executor - program within the node which runs the program
	- Types of operations on RDD
		- Transformations
			- Returns new RDDs as a result
			- Lazy - wont compute until needed
			- Enables to optimize the operations for Spark by "Reorder the computations when required"
			- Enables spark to recover from stragglers and failures
			- Map, filter, distinct, flatMap (returns a sequence)
		- Actions 
			- Compute a result based on RDD and store on HDFS
			- Eager - Result is computed immediately 
			- Reduce, Take(n) = return array with first n ele, collect = return all ele as array, TakeOrdered(n, asc) = return first n ele in asc order
		- Persist - RDD to memory

- Kafka
	- MapReduce and Spark is very similar to Batch Processing, which can be parallelized
	- In the world of microservices or any computation system, which involves multiple message transfers between the components, then 
		- RPC wouldn't work, as RPC directly couples the sender and the receiver
		- RPC is a form of Direct communication
	- There are 2 modes of communication
		- Direct communication - Sender and the receiver are in the same space and time, where the sender expects the receiver to be online and reply back
		- Indirect communication - The above requirements are not held
			- Time uncoupling
				- Sender can send the message even if the receiver is not available
				- Allows us to deal with network partitions and volatile environments
			- Space uncoupling 
				- Sender sends the message but doesn't know to whom its sending
				- Allows us to deal with addition/ change of nodes
	- Pub-Sub basically falls in the category of "Time uncoupled and Space uncoupled"
	- Two types of subscription models
		- Topic Based
			- Events/ messages are classified into predefined topics, where the subscription receives events from certain topics
			- Uses only one constraint = Equality of the topic name
		- Content Based
			- Events/ messages has multiple attributes which do then get categorized accordingly
			- Uses multiple constraints over data such as equality, regex, etc
	- We don't use the concept of "Centralized server" in pub sub, due to the distributed system problems such as Reliability, Replication and fault tolerance.
	- Kafka solves this problem by creating a network of brokers in between which solves time, space coupling as well as the distributed system problems
	- Event routing algorithms - Algorithms which distribute the events from pubs to subs
		- Flooding
			- Broadcasting all the events to all the nodes, where the individual node filters the data accordingly
			- Uses underlying multicast framework to achieve this
			- Can result in lot of unnecessary traffic
		- Filtering
			- Publisher basically sends to the nearest broker, which in turn maintains a routing table for all the brokers/ subscribers, based on the subscriptions
			- So, the broker applies a filtering/ matching function before sending to subscriptions based on the subscription they have
			- The challenge is that it doesn't scale well with number of subscriptions, and if the subscriptions change, there has to be a lot of changes across the broker network
		- Rendezvous
			- These are the specific broker nodes, which handles the subset of event space
			- The routing tables are only present on the rendezvous nodes, and they are built for it
			- Pub and Sub nodes basically have compute functions
				- Subscription Node(s) = SN(s), which takes a subscription and returns the rendezvous node responsible for that subscription
				- Event Node(e) = EN(e), which takes a event, returns the rendezvous node responsible for matching event against the subscriptions in the system
				- Can be challenging for content based subscriptions
	- Kafka 
		- Consumers poll data rather than the brokers pushing the data. It simplifies the idea of backpressure
		- Data/ Records is categorized as topics (topic is a stream of records), where each of the topic is split as partitions, and each of the partitions are again replicated
		- Within the replicas, it generally uses the Leader-follower pattern, where the leader handles the writes and followers handles the reads
		- Partitions are "Append only log"
		- Producer chooses which partition to send the record to (Such as Hash of Key) and also sends the records at their own pace
			- Fire and Forget - Very Fast
			- Synchronous Send - Blocks the message send for others
			- Asynchronous send
