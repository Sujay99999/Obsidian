- Spark
	- Drawbacks of Mapreduce leading to Spark
		- One of the biggest drawbacks for the mapreduce is for the iterative computation of large datasets, where we use the disk storage to hold intermediate results, even though we had great flexibility, but it had huge overhead
			- Understand Relative cost of using In memory vs Disk and Network
		- Iterative operations on a graph is also not recommended
			- There was an explosion of Models over here with different features, why cant we have them all
	- How Spark solves them all
		- How in-memory computation works
			- Keep and the share the datasets in the main memory
			- Why this was not thought in first place for mapreduce = because of volatility and inability to store the pre and post mutations of the data
		- Inability to store the pre and post mutations of the data
			- First of all we dont need to store intermediate data if we know we can derive them back from the source
	- We solve it using RDD (resilient distributed datasets)
		- RDD only has few operations - map, groupBy, filter, sample, flatMap
		- So, if there is any issue with the data, we can traceback to the previous checkpoint that can be a cache or source, and reapply those computations exactly on that particular shard of data
		- RDD are immutable, and deterministic
		- RDD are compatible with HDFS as well, as they support streaming Appends
	- How RDD solves Fault tolerance
		- RDD has 2 properties
			- Immutability - once constructed, cant be changed
			- Allow only Functional transformations - map, filter, reduce which are deterministic and can run in parallel
	- Spark Job Architecture and components
		- Driver program - main program/ application
		- Context - Sparkcontext - handle to the spark cluster
		- Worker program - Program that runs on the cluster nodes
		- Executor - program within the node which runs the program
	- Types of operations on RDD
		- Transformations
			- Returns new RDDs as a result
			- Lazy - wont compute until needed
			- Enables to optimize the operations for Spark by "Reorder the computations when required"
			- Enables spark to recover from stragglers and failures
			- Map, filter, distinct, flatMap (returns a sequence)
		- Actions 
			- Compute a result based on RDD and store on HDFS
			- Eager - Result is computed immediately 
			- Reduce, Take(n) = return array with first n ele, collect = return all ele as array, TakeOrdered(n, asc) = return first n ele in asc order
		- Persist - RDD to memory

- Kafka
	- MapReduce and Spark is very similar to Batch Processing, which can be parallelized
	- In the world of microservices or any computation system, which involves multiple message transfers between the components, then 
		- RPC wouldn't work, as RPC directly couples the sender and the receiver
		- RPC is a form of Direct communication
	- There are 2 modes of communication
		- Direct communication - Sender and the receiver are in the same space and time, where the sender expects the receiver to be online and reply back
		- Indirect communication - The above requirements are not held
			- Time uncoupling
				- Sender can send the message even if the receiver is not available
				- Allows us to deal with network partitions and volatile environments
			- Space uncoupling 
				- Sender sends the message but doesn't know to whom its sending
				- Allows us to deal with addition/ change of nodes
	- Pub-Sub basically falls in the category of "Time uncoupled and Space uncoupled"
	- Two types of subscription models
		- Topic Based
			- Events/ messages are classified into predefined topics, where the subscription receives events from certain topics
			- Uses only one constraint = Equality of the topic name
		- Content Based
			- Events/ messages has multiple attributes which do then get categorized accordingly
			- Uses multiple constraints over data such as equality, regex, etc
	- We don't use the concept of "Centralized server" in pub sub, due to the distributed system problems such as Reliability, Replication and fault tolerance.
	- Kafka solves this problem by creating a network of brokers in between which solves time, space coupling as well as the distributed system problems
	- Event routing algorithms - Algorithms which distribute the events from pubs to subs
		- Flooding
			- Broadcasting all the events to all the nodes, where the individual node filters the data accordingly
			- Uses underlying multicast framework to achieve this
			- Can result in lot of unnecessary traffic
		- Filtering
			- Publisher basically sends to the nearest broker, which in turn maintains a routing table for all the brokers/ subscribers, based on the subscriptions
			- So, the broker applies a filtering/ matching function before sending to subscriptions based on the subscription they have
			- The challenge is that it doesn't scale well with number of subscriptions, and if the subscriptions change, there has to be a lot of changes across the broker network
		- Rendezvous
			- These are the specific broker nodes, which handles the subset of event space
			- The routing tables are only present on the rendezvous nodes, and they are built for it
			- Pub and Sub nodes basically have compute functions
				- Subscription Node(s) = SN(s), which takes a subscription and returns the rendezvous node responsible for that subscription
				- Event Node(e) = EN(e), which takes a event, returns the rendezvous node responsible for matching event against the subscriptions in the system
				- Can be challenging for content based subscriptions
	- Kafka 
		- Consumers poll data rather than the brokers pushing the data. It simplifies the idea of backpressure
		- Data/ Records is categorized as topics (topic is a stream of records), where each of the topic is split as partitions, and each of the partitions are again replicated
		- Within the replicas, it generally uses the Leader-follower pattern, where the leader handles the writes and followers handles the reads
		- Partitions are "Append only log"
		- Producer chooses which partition to send the record to (Such as Hash of Key) and also sends the records at their own pace
			- Fire and Forget - Very Fast
			- Synchronous Send - Blocks the message send for others
			- Asynchronous send
		- Messages in Kafka are poll based, which improves the throughput by batching
		- Consumers read the data from the partitions by "pulling the updates", which enables to design for "average load" rather than peak load, and its done by storing the read offsets for each partition
		- More partitions = More parallelism = More performance for consumers
		- No -order guarantee for records across per-topic partitions
		- Kafka guarantees "At-least once delivery"
		- Replicas in kafka are only preventing data loss, doesnt impact parallelism
		- The Acks required for producer to commit the messages (for all replicas), determine the latency vs durability tradeoff
		- Kafka uses zookeper/ raft to store the metadata



- Security in Distributed Systems
	- What is Security mean
		- Confidentiality: An adversary shouldn't read the messages
		- Integrity: An adversary can't tamper the message without being detected
		- Authenticity: How does the sender/ receiver know that the message comes from the person it came from
	- Symmetric Key Model
		- Sender and Receiver have a pre-shared secret key
		- Confidentiality - Use encryption algorithms to encrypt the M with K to produce C and vice versa
		- IND-CPA is a technique to understand if the encrpyption is secure or not i.e.,
			- Adversary basically sends Alice two different messages M0 and M1 and asks Alice to encrypt using the K it has.
			- Then once the adversary gets back C0 and C1, if the adversary is able to predict the K by more than 1/2, then the encryption is compromised
		- One time pad i.e., Encryption  = XOR of K and M passes IND-CPA if the keys are used for one time only. If we use more than one time, it compromises the encryption
		- Block ciphers modes of operation
			- Generally, we can encrypt the messages using the Block ciphers, even though they don't fall under the perfect security, it is very hard to break by the computationally bounded adversary
			- There are 2 modes of operations
				- ECB - Electronic Code Book
					- We chop the Message into pieces of N bits, and each chunk is encrypted with K bit key
					- Not IND-CPA secure, as the encryptions are deterministic
				- CTR - Counter Mode Encryption
					- In addition to the chunk of N bits, we add a unique running counter to get that randomness in the output
					- IND-CPA secure
			- ECB and CTR ensure confidentiality, but lacks authenticity and integrity
		- MAC - Message Authentication Codes
			- MAC is similar to Checksum for the content, where the Sender sends both the encryption of message and MAC as well
			- Hash functions are deterministic and fast to compute
		- Authenticated Encryption is technique that uses both MAC and encryption to guarantee Confidentiality and Integrity. This still suffers from Authenticity due to replay attacks
		- we can prevent replay attacks by using Nonce
	- Asymmetric cryptography
		- The key is split into 2 parts - Public key and Private key
		- Everyone can encrypt using the public key, where as the receiver can only decrypt it
		- Digital signatures provide integrity similar to MACs for symmetric encryption
	- TLS - Transport Layer Security
		- TLS uses both Asymmetric to bootstrap the symmetric keys and Symmetric crypto for fast communication
		- Issues with TLS
			- Forward Secrecy - If the messages are recorded now, and broken in future, will it compromise the transactions due to the fact that we used Long term keys
			- Authenticity - How can client get server's public key safely
		- DH Key exchange
			- Solves Forward secrecy because of the fact the secrets a and b are used per sessions
			- Relies on the fact that Its hard to crack to Discrete Log problem
			- Not secure against Man in the middle attack
		- PKI enables authenticity for Public keys, where they provide certificates (binds the public key to another entity E)
		- Steps for TLS
			- Client performs a handshake with Server as part of TCP along with Rb and Rs. The Rb and Rs are called randomness to prevent replay attacks
			- Server sends the certificate to client, through which the client gets the server's public key. Along with certificate, server also sends the DH key signed with its private key i.e., {g^a mod p}PriK(server), to prevent MITM attack
			- Client similarly sends the g^b mod p
			- Client and server each derive the symmetric keys from Rb, Rs and PS
			- Client and server now exchange MACs
			- Client and server now communicate using Authenticate encryption 


- Internet Content Delivery
	- DNS
		- Early version: Maintain a text file called "hosts.txt", where the servers retrieved updated list every time to maintain the host names
		- Goals of the DNS = Scalability, Highly Available and Correctness + Fast lookups
		- DNS has Hierarchical Distribution, which is opposite of Flat namespace, Centralized administrator and Centralized storage
		- How Hierarchal distribution/ namespace works
			- Top level Domains
				- Registered globally
			- Domain names
				- Can be registered from the authority managing a top level domain
			- Subdomains
				- Managed by Domain administrator
		- DNS Zones 
			- Contiguous section of the namespace
			- Managed by the specific organization
			- Each zone has an associated set of name servers, which are responsible for keeping the domain name i.e., IP address mapping for that zone
			- DNS root is at the top of all zones, which is managed by 13 root name servers
			- Root servers don't store all the domain names, instead they delegate the authority to the next level name servers
			- Authoritative name servers keeps the mapping from Domain names to IP address
		- DNS Resource Record = < Class, Name, Value, Type, TTL >. Class is always IN (Internet)
			- Type A: Name is Hostname and value is IP address
			- Type NS: Name is Domain and Value is Name of Authoritative name server
			- Type CNAME: Name is Alias name, and value is Canonical Name
		- Each host basically connects to the Local DNS servers, which answers all the DNS queries about the Local zone, providing the IP addresses and for the Non-local domain names, it finds it and caches the response
		- What Happens when Local DNS server wants to find Non-local Domain name
			- Iterative DNS query
				- DNS server queries every necessary name server for the final IP mapping
			- Recursive DNS query
				- DNS server completes the request on the requestor's behalf
		- Servers high in the hierarchy use iterative queries, as they deal with large loads, and servers low in the hierarchy use recursive queries
		- Caching is important in scaling the DNS
			- Cached DNS records expire based on TTL
			- Top level NS records have very high TTL; Intermediary NS records have High TTL; Low records have small TTL
			- Long TTLs alleviate load on root, where as the Tiny TTLs help in fault tolerance and load balancing
	- CDN
		- Edge servers
			- Servers that connects the users/ hosts to the servers
		- Core servers
			- Servers that have high capacity, massive bandwidth, helps route data from origin servers to the edge servers
		- Where to Cache Content
			- CDN works with the ISPs to install PoP (Points of Presence), which brings the content closer to the user
			- User retrieves the data by first contacting the closest edge location/ PoP, and the cache miss will lead to core servers and then the origin server
		- How to direct the clients towards the PoP
			- Using DNS based Indirection
				- Load balancing - Mapping multiple IP addresses to the same name to reduce load
				- Performance optimization - Configure DNS server to serve different IP addresses based on the region
				- Multiplexing - Same IP address can have multiple DNS names
		- How to choose a CDN server within a CDN edge location i.e., How does the PoP cache huge amount of data
			- Can use Load balancing i.e., PoP has a set of Local cache servers, where the requests are distributed amongst them
			- If a local cache server, then it retrieves from the origin server and cache it
			- Load balancing with Round Robin
				- Can have high cache miss rate leading to low cache storage efficiency
			- Load balancing using Static Partitioning based on Key
				- Can create skew based on keys
			- Load balancing using Hash Partitioning
				- Creates even distribution, but Can make adding/ removing the servers very hard
			- Load balancing using Consistent hashing - Best Solution


- BFT
	-  Byzantine Broadcast properties
		- Termination: Every honest node eventually halts with some output
		- Agreement: All the honest nodes will halt with the same output 
		- Validity: If the leader is an honest node, then the common output of the honest nodes is the private input v* of the leader
	- BFT feasibility basically depends on the setup of the nodes
		- Network Setup
			- Sync Network: All the messages are received within a bounded time; Have a shared global clock
			- Async network: Messages can take a infinite amount of time to deliver but will get delivered at the end; No Shared global clock
			- Partially Sync: The network basically starts as an Async mode and transitions into sync network after a point called GST (Global Sync Time)
		- Presence of PKI
			- If PKI is present, we can ensure that the output of the nodes can't be forged
